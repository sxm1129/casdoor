# Casdoor 系统架构说明书 (System Architecture Specification)

## 1. 架构概述 (Architecture Overview)
Casdoor 是一个基于 Go (后端) 和 React (前端) 构建的，支持多租户 (Multi-Tenant) 的身份和访问管理 (IAM) / 单点登录 (SSO) 平台。它的核心设计理念是“以应用和组织为中心”，将用户、身份提供商 (IdP) 和权限控制解耦，并通过高度可配置的层级关系进行管理。

在技术栈上，Casdoor 采用：
- **后端**：Go 语言，基于 Beego Web 框架。
- **持久层**：XORM (支持 MySQL, PostgreSQL, SQLite, SQL Server 等多种关系型数据库)。
- **前端**：React + Ant Design (独立的静态单页应用)。
- **交互协议**：RESTful API。

## 2. 核心领域模型 (Core Domain Models)

### 2.1 多租户与层级关系
- **Organization (组织)**: 多租户隔离的最高层级边界。每个组织拥有独立的用户池、密码策略、LDAP 配置、主题皮肤等。
- **User (用户)**: 用户属于且仅属于一个特定的 Organization。用户作为登录主体，拥有密码、MFA(多因素认证)和各种基础资料。
- **Application (应用)**: 代表一个需要接入 Casdoor 进行 SSO 的下游业务系统。一个应用可配置支持多个不同的登录提供商(Provider)和注册表单项。
- **Provider (身份提供商)**: 本地或第三方的认证源，例如 GitHub、微信、钉钉、LDAP、SAML 等。应用和提供商是**多对多**的映射关系。

### 2.2 身份与映射机制 (User Identity)
经历了底层的架构演进，Casdoor 的用户扩展身份数据已完成**无缝解耦**:
- `user` 表仅存储组织基础核心信息(如 Name, Email, Phone, Password, Avatar 等)。
- **`user_identity` 映射表**:  专门存储第三方 IdP 登录（如 WeChat、Lark 等）绑定到 Casdoor 的用户关联数据，包括 `provider_type` 和 `provider_id`。这样有效解决了“神对象”带来的数据冗余。
- **内存/JWT Property**: 所有的第三方属性及 Access Token 以 JSON 格式动态持久化在 User 的 `properties` 字段中，通过统一的 JWT Custom Claims 返回给下游业务应用。

### 2.3 RBAC 权限控制流 (Role-Based Access Control)
Casdoor 实现了强大的、具有独立查询层优化的 RBAC:
1. **模型定义**:
   - `Role (角色)`: 一组权限的集合。
   - `Permission (权限)`: 对特定 Resource (资源) 和 Action (动作，如 Read/Write) 的控制定义。可被设置为“允许”或“拒绝” (Allow/Deny 机制)。
2. **关系映射**:
   - 采用标准的三张物理映射表：`user_role`, `role_permission`, `user_permission`。
   - 这在彻底消除了底层大表 `LIKE` 查询带来的严重性能瓶颈的基础上，实现了对高并发场景极具友好的 JOIN 联查。

## 3. 核心功能及执行流 (Core Workflows)

### 3.1 单点登录与 OIDC (Single Sign-On / OIDC)
Casdoor 原生内置了完整的 OAuth 2.0 和 OIDC (OpenID Connect) Provider 支持：
1. 客户端通过标准 OIDC 协议引导用户重定向至 Casdoor 的 Auth 页面。
2. Casdoor 识别该应用 (Application) 配置的可用 Provider，展示登录项。
3. 用户登录后，Casdoor 基于安全哈希与状态记录发放 `Authorization Code`。
4. 下游应用换取 `AccessToken` (由 JWT 构成) 与 `IdToken`，并在此时执行配置在 App 层的自定义 Token Claim 填充。

### 3.2 同步机制 (Syncers)
Casdoor 架构包含了强大的企业通讯录同步层 (`syncer.go`)：
- **实时与定时拉取**: 可以通过 API 定时 (Cron) 去钉钉、飞书、企业微信或 Active Directory (LDAP) 拉取最新的人员变更。
- **只读设计**: 默认向 Casdoor 单向流入数据，将第三方雇员 ID 挂载至 Casdoor 用户体系的 `properties` 中，自动完成企业人员的上云。

### 3.3 通用认证及网关 (Authentication Gateway / Proxy)
除了身份存储，Casdoor 系统中还包含：
- **会话限流 (Session Limiting)**: 可以通过策略限制同一用户单点/多点活动 Session，防多地非法登录。
- **防暴力破解 (Check Check)**: 集成在 `check.go` 内的安全流拦截错误密码风暴。
- **日志审计与回调 (Audit Log & Webhooks)**: 所有通过的写操作（新增组织、修改用户）均由 `record.go` 进行异步收集，通过配置好的 Webhook 以事件驱动的形式推送至外部安全中心或监控平台。

## 4. 选型评估与维护性
系统的强扩展性（无绑定提供商、纯 API 驱动）使其成为内网零信任演进和 C 端产品账号底座的理想架构选型。当前代码不仅实现了逻辑与数据结构的分离，且经过高频高危操作层的安全性生产审计，属于健壮度极佳的生产级工程。
